# Brewline build — root cause of the time, the cost and the false alarms (2026-10-24)

Traced from the build's own records: `logs/events.jsonl` (every tool call with a timestamp), the worker logs (every model
call with its duration), `rounds.jsonl` (every finding of every review round), the dispute files, the spend table and the
agents' instructions. Nothing below is estimated unless it says so.

## 1. Where the time went

Request at 11:16, spec approved 11:25, plan 11:32, builders 11:55–13:22, code review 13:22–15:18, first deploy done
15:44 (4.5 h), then live review rounds. Model calls over the whole build: 1,099 (1,001 ok, 98 failed). A single agent
building the same app makes roughly 60–100 calls (estimate).

| Cause | Evidence | Cost in time |
|---|---|---|
| Builders run in lockstep phases: both must finish phase N before either starts N+1 | Shubham idle 54 of its 86 min, each idle stretch starts at its own phase end | ~54 min |
| One action per model call, every call resends the whole conversation | Aanya 268 calls with 1 tool each; 117 were single-file reads (each phase is a new run that re-reads its own files) | ~45 min (Aanya), ~20 (Shubham) |
| Failed model calls | 98 failed calls, 123 min lost; Navya (logic review) failed 41 times (120 s timeouts on the one-pass review), 52 min | 123 min |
| Rate limits | 89 "429, retrying in the backup region"; the backup region lacks two models (404) | included above |
| Each builder starts its own containers to check each phase, then Riya deploys again | 12 docker runs per builder; Riya's deploy took 25 min and 46 calls on a 30B model | ~30 min |
| Open-ended review loop | 5 code-review rounds (~2 h) + 4 live rounds (~45–60 min each), see section 2 | ~5 h |

## 3. Why the checkers raise false alarms

- **A quota.** The live evidence collector is told "List AT LEAST 3-5 concrete issues". Every live round reported
  exactly 5.
- **Fail by default.** The reality checker is told "Default to NEEDS WORK" and "add anything real that Stage 1 missed".
  The agent meant to verify claims is told to add claims.
- **No yardstick.** The live checkers are not given the approved spec/plan to judge against; the code reviewers get it as
  context but nothing requires a finding to name the plan item it breaks.
- **No proof needed.** In its last run the reality checker never opened app.ts, auth.routes.ts or the orders routes, yet
  quoted lines from them and from files that do not exist; it called /api/menu (the real path is /api/v1/menu) and
  reported "16 returned items" — the only 16 it saw was a list of 16 files. Nothing checks that a cited file exists or
  that quoted code is in it. The only false-finding filter handles import claims, and only in the code review.
- **The Chief AI verifies only when asked.** Its dispute settler runs only when a builder disputes a finding. It ruled 3
  of 3 disputes "not true" — after each had already cost a round.

## 4. Why work reached the review unfinished

- **The approved design was lost.** The design agent produced the brief, but the generic completion gate (built for
  builders: "no verification evidence this run") rejected it twice; it rewrote its answer as prose, the parser could not
  read it, and the system used a fallback brief without stopping. The site rendered the stock purple (#5522CC) instead of
  the approved palette.
- **The cheap checks run late.** Emoji, dead-button, page sweep (overflow, failed requests) and spec-colour checks run
  in the review stages, not as each builder's exit check.
- **Checker sub-steps could write.** Fixed 2026-10-24 (batch 17); its leftovers `update.js` and `verify.js` are still in
  the project folder.

## 5. My own part

I fixed what each paid run exposed, one symptom at a time, and started the next paid run, instead of tracing a whole
build end to end like this before spending more. This trace should have been done after the first failed run.

## 7. More causes found in this pass

- **The approved plan contradicted itself.** The spec text holds the café palette (#FAF6F0, Fraunces); the design brief
  shown at approval was the silent fallback ("Confident and precise — a technical product", green, Inter). The design
  agent's first answer was the café brief; the builder completion gate rejected it (`completion-gate.ts:56`).
- **Lockstep in code:** `pipeline/workflows/project-build.ts:589-595`, `await Promise.all(phasePromises)` per phase.
- **A check that reports success without checking:** `agents/riya/src/index.ts:1833` skips a resource whose create is
  refused (`continue`), then prints "every resource's create/read/update/delete confirmed". On Brewline menu create
  answered 403 and was never checked.
- **Model failures are mostly ours, not rate limits:** 43 calls hit the 120 s timeout (86 min; 23 of them Navya's one-pass
  review, up to 600k characters, same 120 s limit as a short call); 36 failed with 404 in the backup region our router
  jumps to after a 429 (13 min) — Google's guidance is to back off on the global endpoint, the regional endpoint has the
  most 429s and lacks these models; the 429s themselves cost about 2.4 min.
- **Agents in parallel start on the same model:** one pool per tier (`router.ts:200-205`); all three reviewers start on
  gemini-3.1-pro, both builders on the same flash model.
- **Deploy:** the deploy agent wrote a ~1 KB compose file in 3 runs (16, 19, more calls), re-reading the same files each run.

## 8. Security, checked live

| Finding | Evidence | Risk |
|---|---|---|
| Dev stack open to the network | Running containers listen on 0.0.0.0: Temporal 7233, Temporal UI 8088, Redis 6379, Postgres 5434; the compose file already says 127.0.0.1 but the containers were never recreated; network profile Public; Docker Desktop has an inbound allow rule on Public; Redis answers PING without a password | anyone on the same Wi-Fi can reach the build queue and its history |
| Agent commands run on the host | `run_command` spawns on the host; allowed: node, npx, npm, bun, curl, git; the container sandbox covers only the type check and verification commands | a misled agent can run any Node code (the checker's sub-check did, and changed the DB) |
| Google key path given to agent commands | `GOOGLE_APPLICATION_CREDENTIALS` is not on the block list (`sandbox-env.ts`); the list is a deny-list, so any new secret passes | key file reachable by agent code |
| A secret in logs and model text | the deploy agent's summary "Updated JWT_SECRET to …" — the value appears 6 times in Brewline's pipeline.log and is saved in its history | delivered app's signing secret exposed |
| Leftover files with the DB password | `update.js`, `verify.js` in Brewline's project folder (written by the checker's sub-check), each with the connection string and password | shipped to the customer |
| Retry has no owner check | `/api/pipeline/:id/retry` needs sign-in but not ownership | any signed-in user can retry any build (single user today) |
| Generated apps | bind 127.0.0.1; Brewline has helmet, CORS limited to its frontend, rate limit on auth | fine |

## 9. A second Google project as rate-limit fallback

Not recommended, on facts: on pay-as-you-go Vertex a 429 means Google's shared pool is busy, not that the project hit a
fixed quota, so a second project draws on the same pool; Google's API terms say users will not attempt to circumvent
usage limits, and one project here was already flagged once; and in this build the 429s cost about 2.4 min — the 99 min
of failures came from our own timeout and backup-region handling. The supported ways to more capacity are backoff on
the global endpoint, Provisioned Throughput or Priority PayGo (paid), or asking Google for more.
