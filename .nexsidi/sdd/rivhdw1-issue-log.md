## Issues found this run

### 1. (Fixed at the source, not just per-project) `proxy.ts` vs `middleware.ts` — root cause was in the SCAFFOLD ITSELF, not agent judgment
- **What broke:** Observed live, mid-generation: Aanya editing a file literally named `proxy.ts`. Investigation found the root cause is NOT an Aanya judgment call — `writeStaticScaffold` (agents/generators/aanya/src/index.ts) mechanically writes the auth-middleware file to `path: "proxy.ts"` as part of the STATIC pre-written scaffold, before Aanya's own agent loop even starts. Worse: her system prompt's own Rule 8 explicitly said "NEVER create a middleware.ts file... Next.js rejects having both proxy.ts and middleware.ts present" — a confident, detailed, but FALSE claim. Next.js 16.2 simply never invokes a file named proxy.ts at all; middleware.ts is the only recognized convention (confirmed directly this session via real request logs on a live deploy: only middleware.ts received traffic).
- **Who caused it:** Whoever originally wrote this scaffold + prompt rule (predates this session) got the Next.js convention backwards and encoded it confidently into both the deterministic scaffold-writer AND the prompt's explicit rules.
- **Did QA catch it:** Yes, reactively — Navya has correctly flagged this exact defect on at least one earlier project (freshtst1) this session, and Aanya "fixed" it via a QA-triggered rename. But the fix was never applied to the SOURCE (scaffold + prompt), so every NEW project paid the same expensive QA round-trip to rediscover and re-fix the identical bug. This run (rivhdw1) was actively repeating that exact cycle when caught.
- **Root cause:** A factually incorrect belief about Next.js 16.2's middleware file-naming convention, hardcoded into both the deterministic scaffold and the prompt's explicit rules, with no test ever checking it.
- **Fix:** `writeStaticScaffold` now writes to `path: "middleware.ts"`. Prompt Rule 8 corrected to forbid `proxy.ts` and require `middleware.ts` (the opposite of before). Two new regression tests: one confirms the scaffold writes to the real filename, one confirms the prompt no longer contains the false "never create middleware.ts" claim. 876/876 full suite passing.
- **Status:** FIXED AT THE SOURCE. Not retroactively applied to rivhdw1's already-in-progress generation (the worker had already loaded the old code before this was found; restarting mid-activity would have discarded real progress) — this run will still pay the one-time QA round-trip cost, but every project generated AFTER this fix (including any retry of this exact stage) will get it right from the start. This is the exact "self-fix at the source, don't rely on QA every time" principle the user asked for, applied to a bug that was silently costing every single project a wasted round-trip.

### 2. Self-inflicted operational bug: two duplicate worker processes silently running simultaneously
- **What broke:** After the workflow failed (Aanya max-iterations) and was relaunched, `runShubham`'s activity was scheduled but never started, `runPranav` failed twice, and generation behaved inconsistently despite identical code. Investigated via Temporal's REST API (workflow history + describe/pendingActivities), which showed `runPranav`'s executing worker identity used a DIFFERENT build/process than expected.
- **Who caused it:** Me. Earlier tonight, when I found a stale worker-lock referencing a dead PID, I deleted `.nexsidi/worker.lock` and started a new worker — correct that time, since the old PID was genuinely dead. Later, when restarting AGAIN to load the middleware.ts + generation-retry-signal fixes, I repeated the same "delete lock, start new worker" move WITHOUT verifying the previous worker was actually dead this time — it wasn't. Confirmed via `Get-CimInstance Win32_Process`: two real `bun.exe` processes (Windows PIDs 31488 and 30312 — neither matching the PIDs Git Bash's `$!` had reported, which is a known Git-Bash-on-Windows PID-reporting quirk) were both alive and polling the SAME Temporal task queue simultaneously, one running stale pre-fix code, one running the latest code. Temporal round-robins activity dispatch across all registered pollers with no way to prefer one — so different activities within the SAME workflow run were nondeterministically executed by different code versions.
- **Did QA catch it:** N/A — this is infrastructure/process hygiene, not something any pipeline QA layer could see.
- **Root cause:** Trusting `$!` (Git Bash's reported PID) as ground truth for whether a background process is still alive, instead of directly verifying via the real OS process list before taking the destructive "delete the lock and start a new poller" action.
- **Fix:** Killed both real Windows PIDs directly via `Get-CimInstance`/`Stop-Process`, confirmed zero `bun.exe worker.ts` processes remained, THEN started exactly one new worker and confirmed via `Get-CimInstance` again that exactly one exists.
- **Status:** Fixed operationally. Worth noting for future sessions: on Windows/Git-Bash, always verify via `Get-CimInstance`/`Get-Process` before assuming a background process is dead — `$!`'s reported PID is not reliable here.

### 3. REAL, SERIOUS SECURITY BUG found live in generated code: unauthenticated privilege escalation via register
- **What broke:** Confirmed by directly reading `backend/src/controllers/auth.ts`: `register()`'s Zod schema accepts `role: z.enum(["customer","admin"]).optional()` from the PUBLIC (auth:false) endpoint, and the handler inserts whatever role the caller sent with ZERO guard — no check for whether an admin already exists, no `adminSecret`, nothing. Any anonymous caller can POST `{"role":"admin", ...}` to `/api/v1/auth/register` and instantly gain full admin access (catalog management, order management).
- **Who caused it:** Shubham. Arjun's contract-security-gate (issue #22 in the earlier freshtst1 log context) had correctly STRIPPED the `role` field from the public register endpoint's documented TYPED contract specifically to prevent this. Shubham, reading the full spec (which legitimately requires admin accounts to exist for the "Store Admin" features), added the field back based on real business need — but without the safe-bootstrap guard pattern (lock table, check no admin exists yet, reject if one does) that an EARLIER project (freshtst1) had implemented correctly for the identical requirement.
- **Did his own self-check catch it:** No — and this is instructive, not just a miss. Shubham's strengthened LIVE AUTH-BOUNDARY VERIFICATION (built earlier tonight) tests "does calling a protected route WITHOUT a token correctly 401/403" — an AUTHENTICATION question. This bug is a PRIVILEGE-ESCALATION / AUTHORIZATION bug (a fully authenticated, legitimate-looking request that grants itself excessive privilege) — a genuinely different vulnerability class self-checks focused on "is auth enforced" don't test for. This is real, live evidence for the point made earlier this session: self-checks catch the obvious stuff (missing auth entirely); adversarial security review (Karan) exists specifically for subtler authorization bugs like this one.
- **Status:** CONFIRMED CAUGHT BY QA. Karan's Stage 5 findings included: "[security/auth] Mass assignment / privilege escalation vulnerability in user registration schema" — the exact bug, correctly identified, on the first QA pass. Real, live confirmation that self-checks (auth-boundary testing) and adversarial security QA (Karan) genuinely cover different vulnerability classes, exactly as reasoned earlier tonight — this is not a QA gap, the layered architecture worked as designed.
